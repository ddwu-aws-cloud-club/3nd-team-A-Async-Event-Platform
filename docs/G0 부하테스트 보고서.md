## 1. 테스트 목적

본 G0 부하 테스트의 목적은 다음 한 가지를 증명하는 것이다.

> 트래픽 급증 상황에서 시스템이 에러로 요청을 거절하지 않고, 큐(SQS)로 흡수하여 비동기 처리 흐름을 유지할 수 있는지
>

이를 위해 G0 단계에서는 의도적으로 다음 설계 기준을 채택했다.

- Ingest API는 요청 처리 결과와 무관하게 **즉시 202 Accepted**를 반환한다.
- Worker가 처리하지 못하는 동안에도 요청은 **유실되지 않고 큐에 적재**된다.
- G0의 검증 대상은 “정확한 성공 건수 집계”가 아니라, **처리 흐름이 끊기지 않는지**이다.

---

## 2. 테스트 환경 및 전제

### 2.1 트래픽 주입 방식

- 도구: k6
- 부하 형태: Spike Load(스파이크 부하)
- 설정
    - VUs: 300
    - Duration: 60초
    - Target API: `POST /events/EVT-009/participations`

### 2.2 멱등성(Idempotency)을 고려한 k6 구성

Ingest API에는 `(eventId, userId)` 기준 멱등성 방어가 구현되어 있으므로,

부하가 멱등성에 의해 소실되는 상황을 방지하기 위해 다음을 보장했다.

- 매 요청마다 서로 다른 userId 사용
- 각 VU는 시작 시 1회 로그인 후 토큰을 캐싱하여 재사용
- 동일 userId로 인한 중복 요청 발생 차단

이를 통해 모든 요청이 **실제 트래픽으로 큐에 적재**되도록 구성했다.

## 4. 테스트 수행 과정 및 결과

### 4.1 Worker 종료 상태에서의 트래픽 주입 준비

부하 테스트 시작 전, 시스템을 다음 상태로 고정했다.

### Worker 프로세스 종료

목적

- Worker가 메시지를 즉시 소비하지 못하도록 차단
- 트래픽이 실제로 SQS에 “쌓이는지”를 눈으로 확인하기 위함

결과

- 메시지는 처리되지 않고 SQS Main Queue에 적재될 준비 상태

### SQS 큐 상태 확인

- ApproximateNumberOfMessagesVisible = 0
- 이전 테스트 잔여 메시지가 없는 상태 확인

### DynamoDB CapacityItem 상태 확인

- 대상 이벤트: EVT-009
- capacityRemaining = 50

Worker가 꺼져 있으므로, 이 값은 테스트 중 **감소해서는 안 되는 상태**다.

이 시점에서 시스템은

**“트래픽은 받되, 처리는 하지 않는 상태”**로 고정되었다.

---

### 4.2 Ingest API 단일 요청 사전 검증

대량 부하 주입 전, Ingest API의 기본 동작을 단일 요청으로 검증했다.

- Postman으로 `POST /events/EVT-009/participations` 호출

확인 항목

- HTTP 202 응답 반환 여부
- response body에 requestId 포함 여부
- status 필드가 응답에 포함되지 않는지 여부

검증 결과

- 모든 요청이 즉시 202 Accepted로 응답
- Ingest API는 요청을 즉시 큐잉 대상으로 전환함을 확인

이 단계는 이후 k6 결과에서 발생하는 모든 현상이

**부하 때문인지, 기본 로직 오류 때문인지**를 구분하기 위한 기준점 역할을 한다.

---

### 4.3 k6 Spike Load(스파이크 부하) 주입

### 4.3.1 k6 실행 구성

k6는 짧은 시간 동안 대량 요청을 집중적으로 주입하도록 구성되었다.

- VUs: 300
- Duration: 60초
- 요청 대상: `POST /events/EVT-009/participations`

### 4.3.2 k6 실행 중 관찰 포인트

k6 실행과 동시에 다음 지표를 집중 관찰했다.

- k6 콘솔 결과
    - http_req_failed 비율
    - check 실패 여부
    - 응답 코드 분포
- SQS Main Queue
    - ApproximateNumberOfMessagesVisible 값 변화

실행 결과

- 모든 요청이 202 Accepted로 정상 응답
- http_req_failed = 0.00%
- check 실패 0건
- k6 실행 직후 SQS 메시지 수가 빠르게 증가

이를 통해 다음을 확인했다.

- Ingest API는 고부하 상황에서도 요청을 거절하지 않음
- 요청은 애플리케이션 내부에서 드롭되지 않고 SQS로 흡수됨

---

### 4.4 Worker OFF 상태에서의 큐 적재 증명

Worker가 꺼진 상태이므로, k6로 주입된 요청은 즉시 처리되지 않는다.

관찰된 현상은 다음과 같다.

- SQS Main Queue의 Visible 메시지 수가 지속적으로 증가
- DynamoDB의 capacityRemaining 값은 변화 없음

이는 다음 사실을 증명한다.

- 부하는 처리 속도와 무관하게 큐에 안전하게 적재됨
- 시스템은 “처리 불가 = 에러”가 아니라

  **“처리 지연 = 큐잉”**으로 대응


---

### 4.5 Worker 기동 후 소비 및 회복 과정

### 4.5.1 Worker 기동

- Worker 프로세스를 기동하여 SQS 메시지 소비 시작

### 4.5.2 관찰된 처리 흐름

Worker 기동 이후 다음 현상이 순차적으로 발생했다.

- SQS Visible 메시지 감소
    - 쌓여 있던 메시지가 점진적으로 소비됨
- DynamoDB CapacityItem 감소
    - capacityRemaining: 50 → 0
- Worker 로그
    - 메시지 파싱
    - 상태 선점 (QUEUED → PROCESSING)
    - capacity 차감 시도
    - 최종 상태 전이 로그 지속 출력

이는 Worker가 큐에 쌓인 메시지를 정상적으로 처리하고 있음을 보여준다.

---

### 4.6 requestId 기준 최종 상태 도달 검증

부하 테스트 중 요청 유실 여부를 확인하기 위해 다음 절차를 수행했다.

- k6 실행 직전에 Postman으로 3~5개의 요청 수동 전송
- 각 요청의 requestId 저장
- k6 + Worker 처리 완료 후 `GET /requests/{requestId}` 호출

결과

- 각 requestId는 최종적으로
    - SUCCEEDED 또는
    - REJECTED 상태 중 하나에 도달
- 중간 상태에 멈추거나 사라진 요청 없음

이는 고부하 상황에서도 **개별 요청이 끝까지 추적 가능**함을 의미한다.

## 6. 관찰된 의문점 및 원인 분석

### 6.1 현상

- capacityRemaining은 50 → 0으로 정확히 감소
- 그러나 SUCCEEDED 상태의 RequestItem은 소수(테스트 시점 기준 약 3개)
- 대부분의 요청은 REJECTED 상태

### 6.2 원인 분석

이는 버그가 아니라 **G0 설계에 따른 의도된 결과**다.

- CapacityItem은 조건부 업데이트로 **정원 정합성의 단일 진실 소스**
- RequestItem은 조회·추적용 엔티티
- 고부하 경쟁 상황에서
    - capacity 차감은 성공했으나
    - 일부 RequestItem은 상태 전이 경쟁에서 밀림

즉,

- 정원 보장은 CapacityItem이 담당
- RequestItem 개수는 집계 기준이 아님

---

## 7. 의문점에 대한 해결 방안 (G1에서의 해소 방향)

G0 부하 테스트에서 관찰된

**“capacityRemaining은 정확히 감소했지만, SUCCEEDED RequestItem 수가 일치하지 않는 현상”**은

버그가 아니라 G0 설계 범위 내에서 의도된 결과다.

G1에서는 이 의문을 다음과 같은 방향으로 해소한다.

### 7.1 집계 기준 전환

- RequestItem은 **조회 및 상태 추적용 엔티티**로만 사용한다.
- 성공/거절/실패 집계의 기준은

  **Worker가 처리 완료 시 발행하는 `ParticipationProcessed` 이벤트**로 전환한다.

- 즉, “성공 건수”는 RequestItem이 아니라 **이벤트의 count(*)**로 정의한다.

### 7.2 Worker 이벤트 발행 고정

- Worker는 메시지 1건 처리 완료 시 반드시 이벤트를 1회 발행한다.
- 이벤트에는 `finalStatus`, `resultCode`, `queuedAt / startedAt / finishedAt`이 포함된다.
- 이벤트 발행 실패는 관측(분석) 계층의 문제로 취급하며,
  본 처리 결과(상태 전이, ack)에는 영향을 주지 않고 로그만 남기고 무시(swallow)한다.

### 7.3 SQL 기반 정량 집계

- 처리 완료 이벤트는 EventBridge → Firehose → S3로 적재된다.
- Athena에서 SQL로 다음 지표를 집계한다.
    - 성공/거절/실패 비율
    - 시간대별 유입량(queuedAt 기준)
    - 처리량 및 p95 Queue / E2E 지연

이를 통해 G0에서 발생한 집계 불확실성을

**이벤트 기반의 일관된 수치**로 설명할 수 있다.

### 7.4 최종 정리: G0의 의문점을 G1에서 어떻게 해소하는가

G0에서 관찰된

**“capacity는 정확히 보장되지만, SUCCEEDED 개수가 맞지 않는 현상”**은

G1에서 **집계 기준을 RequestItem에서 `ParticipationProcessed` 이벤트로 전환함으로써 해결된다.**

- 정원 정합성은 CapacityItem이 보장하고
- 성공/실패 집계는 처리 완료 이벤트가 보장하며
- 운영 지표는 SQL 분석으로 일관되게 산출된다.

결과적으로 G1에서는

G0에서 발생한 의문을 **설계 변경이 아닌 ‘관측 기준 전환’**으로 완전히 해소한다.

---

## 8. G0 단계 해석 기준

G0에서 다음은 **정상 동작**으로 간주한다.

- capacityRemaining이 정확히 0이 되는 것
- over-booking이 발생하지 않는 것
- SUCCEEDED RequestItem 수가 capacityTotal과 일치하지 않는 것

G0의 목적은 숫자 집계가 아니라

**부하 흡수와 처리 흐름 유지**이기 때문이다.

---

## 9. 향후 보완 방향 (G1)

- Worker 처리 완료 시 ParticipationProcessed 이벤트 발행
- 성공/실패 집계는
    - EventBridge → Firehose → S3 → Athena
    - 이벤트 기반 SQL 분석으로 수행
- Source of Truth
    - G0: CapacityItem
    - G1 이후: ParticipationProcessed 이벤트

---

## 10. 최종 결론

본 G0 부하 테스트를 통해 다음이 명확히 증명되었다.

- 시스템은 고부하 상황에서도 요청을 에러로 거절하지 않는다.
- 트래픽은 큐로 안전하게 흡수된다.
- Worker는 큐를 소비하며 시스템을 정상 상태로 회복시킨다.
- 정원 초과 방지는 CapacityItem 기준으로 정확히 동작한다.

RequestItem 기준 성공 건수 불일치는 G0 설계 범위 내의 정상 동작이며,

G1 단계에서 이벤트 기반 집계로 해결될 예정이다.

**결론:**

“부하를 에러가 아니라 큐로 흡수한다”는 G0 목표는 달성되었다.
