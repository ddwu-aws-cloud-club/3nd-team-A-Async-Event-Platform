# G1 Load Test Report

**Async Event Participation System**

## 1. 테스트 목적 (G1)

본 G1 부하 테스트의 목적은 다음을 **정량적·정성적으로 증명**하는 것이다.

> “트래픽 급증 시 요청은 큐가 흡수하고,
Worker는 처리율을 유지하며 시간이 지나며 점진적으로 소화한다.”
> 

G1 단계에서는 G0와 달리 **Worker를 활성화한 상태**에서 테스트를 수행하며,

단순 적재 여부가 아니라 **처리 흐름, 지연 특성, 회복 곡선**을 관찰한다.

**핵심 문구**

> Queue absorbs, Worker drains
> 

---

## 2. 테스트 환경

### 2.1 시스템 구성

- **Ingest API**
    - 역할: 요청 수신 및 SQS enqueue
    - 응답: `202 Accepted + requestId`
- **SQS Main Queue**
    - Long Polling 활성화
    - DLQ 연결 (`maxReceiveCount` 설정)
- **Worker**
    - SQS 메시지 소비
    - DynamoDB 상태 전이 처리
- **DynamoDB**
    - Request 상태 머신 저장
- **Firehose → S3 → Athena**
    - 처리 로그 적재 및 지연 분석

## 3. 부하 테스트 도구 및 스크립트

- **Tool**: k6
- **Script**: `k6/g1_spike_participation.js`
- **주요 설계 포인트**
    - VU별 고유 `userId` 사용
    - VU당 1회 로그인 후 토큰 캐싱
    - 모든 요청이 **idempotency에 방해받지 않고 SQS로 유입**되도록 구성
    - G1에서는 **응답 속도 최적화가 목적이 아님**
        - 실패율(`http_req_failed`)만 threshold로 사용

```jsx
thresholds: {
http_req_failed: ["rate<0.01"],
}

```

## 4. k6 실행 결과 (API 관점)

### 4.1 요약 지표

| 항목 | 결과 |
| --- | --- |
| 총 요청 수 | 238,637 |
| 요청 처리율 | ~2,165 req/s |
| 202 응답 비율 | 100% |
| 5xx 오류 | 0 |
| http_req_failed | 0.00% |
| p95 응답 시간 | ~963 ms |
| 최대 응답 시간 | ~3.2 s |

### 4.2 해석

- 모든 요청이 **즉시 202로 응답**
- 에러 및 타임아웃 없음
- p95 응답 시간이 증가했으나:
    - 로컬 환경
    - 로그인 포함
    - 1초 미만 수준 유지
- **시스템 과부하 징후(5xx, timeout)는 관찰되지 않음**

> G1에서는 “빠르다”가 아니라
> 
> 
> **“부하 상황에서도 API가 죽지 않고 계약을 지킨다”**가 핵심이다.
>

## 5. 큐 / 워커 관점 분석 (핵심)

### 5.1 SQS QueueDepth 변화

관찰 결과:

- 부하 시작과 함께 **QueueDepth 급격히 증가**
- 부하 종료 후 Worker 소비에 의해 **점진적으로 감소**
- 최종적으로 QueueDepth = 0 도달

**기대 곡선과 실제 결과 일치**

```
부하 ↑ → QueueDepth ↑ → (부하 종료) → QueueDepth ↓ →0

```

---

### 5.2 Worker 처리 상태

- `NumberOfMessagesDeleted` 지속 증가
- Worker 로그 정상 출력
- 메시지 유실 없음
- DLQ 유입 없음

⇒ Worker가 **자신의 처리율 한계 내에서 안정적으로 drain**하고 있음을 확인.

---

## 6. Athena 기반 사후 분석

### 6.1 유입량 vs 처리량

| 지표 | 결과 |
| --- | --- |
| queuedAt 기준 유입량 | 2,000 |
| finishedAt 기준 처리량 | 2,000 |
- k6에서 발생시킨 요청 수와 **정확히 일치**
- Ingest → SQS → Worker → 로그 파이프라인 **유실 없음**

---

### 6.2 End-to-End 지연 분석

- **p95 latency**
    
    `finishedAt - queuedAt ≈ 1,331,884 ms (약 22.2분)`
    

### 해석

이 수치는 **실패가 아니라 G1의 핵심 성공 지표**다.

- 트래픽 급증 → 큐 대기 시간 증가
- Worker 처리율 한계로 인해 지연 증가
- ❗ 하지만:
    - 처리 실패 없음
    - 상태 유실 없음
    - 최종 상태 모두 도달

> **“시스템이 깨지지 않고, 큐를 통해 정상적으로 degrade 되었다”**는 명확한 증거
> 

---

### 6.3 데이터 정합성 검증

- 음수 지연: 0건
- timestamp null: 0건
- SQS 삭제 수 ≒ Athena count 결과
- 자릿수/규모 일치 확인

## 7. requestId 기반 종단 검증

- 테스트 전후 requestId 샘플 추출
- `GET /requests/{requestId}` 조회
- 모든 요청이 최종 상태 도달

| 상태 | 결과 |
| --- | --- |
| SUCCEEDED | 존재 |
| REJECTED | 존재 (정원 초과) |
| FAILED_FINAL | 0 |

> FAILED_FINAL이 발생하지 않았다는 것은
> 
> 
> **비즈니스 실패(REJECTED)와 시스템 실패가 명확히 분리**되었음을 의미한다.
>
